# 0.5.2 — Harness budgets

Size: S · Depends on: 0.5.1 · Branch: `task/0.5.2-harness-budgets` · PR title: `0.5.2: enforce run budgets in the harness`

## Goal

The harness enforces all five limits in `adlcv1.Budget` and stops the run
with `STOP_REASON_BUDGET_EXHAUSTED` and the matching `BudgetKind`. A limit of
zero (or a nil `Budget`) means "no limit". The wall-clock limit also
interrupts a model or tool call that is still running.

## Design

### What each limit counts

| Field | Counts | Source |
|-------|--------|--------|
| `max_steps` | completed model calls (`model_call_completed` events) | counted from `recorder.events` (keep a counter in `recorder.add`, incremented for each `model_call_completed`) |
| `max_tokens` | `Usage.InputTokens + OutputTokens + CacheReadTokens + CacheWriteTokens` | `recorder.state.Usage` |
| `max_wall_clock` | `deps.Now() - startedAt` | `startedAt` is a field of the loop's runner, set by `Run` to `deps.Now()` just before `run_started` is written |
| `max_usd_micros` | `Usage.USDMicros` | `recorder.state.Usage` |
| `max_tool_calls` | `tool_call_requested` events (unknown tools count too) | `recorder.state.ToolCalls` |

Every counter comes from the recorded events (or `startedAt`), never from a
loop-local variable that starts at zero. Task 1.7 (resume) relies on this: it
re-reads the old events into the recorder and sets `startedAt` to
`deps.Now() - time already used`, so a resumed run keeps its budget.

### When each is checked

```
before each model call (loop step 5a, after the ctx check), in this order:
    WALL_CLOCK, COST, TOKENS, STEPS
before each tool call (runToolCall step 1, after the ctx check), in this order:
    WALL_CLOCK, TOOL_CALLS
```

A limit is reached when `used >= max` (with `max > 0`). The first one reached
in the order above stops the run.

### Functions (budget.go)

```go
// exhausted describes a reached limit.
type exhausted struct {
	Kind   adlcv1.BudgetKind
	Detail string
}

// usage is what has been spent so far.
type usage struct {
	Steps     int
	Tokens    int64
	USDMicros int64
	ToolCalls int
	Elapsed   time.Duration
}

// beforeModelCall returns the first limit reached, or nil.
func beforeModelCall(b *adlcv1.Budget, u usage) *exhausted
// beforeToolCall returns the first limit reached, or nil.
func beforeToolCall(b *adlcv1.Budget, u usage) *exhausted
```

Both return nil when `b == nil`. Detail strings (tests check them exactly):

| Kind | Detail |
|------|--------|
| STEPS | `fmt.Sprintf("max_steps %d reached", max)` |
| TOKENS | `fmt.Sprintf("max_tokens %d reached (used %d)", max, used)` |
| WALL_CLOCK | `fmt.Sprintf("max_wall_clock %s reached", max)` (`time.Duration` String, e.g. `10m0s`) |
| COST | `fmt.Sprintf("max_usd_micros %d reached (used %d)", max, used)` |
| TOOL_CALLS | `fmt.Sprintf("max_tool_calls %d reached", max)` |

`finish` gains the budget kind: `run_completed{stop_reason: BUDGET_EXHAUSTED,
exhausted_budget: e.Kind, detail: e.Detail}`. Change `finish` to take an
options struct or add `finishBudget(e *exhausted)`; either is fine.

### Wall-clock deadline during a call

If `max_wall_clock > 0`, `Run` derives
`callCtx, cancel := context.WithDeadline(ctx, start.Add(maxWallClock))`
(`defer cancel()`) and passes `callCtx` to `Generate`, `Authorize` and `Call`
instead of `ctx`. When one of those returns because `callCtx` is done:

```
if ctx.Err() != nil            → CANCELLED (the caller cancelled)
else if callCtx.Err() != nil   → BUDGET_EXHAUSTED, WALL_CLOCK, detail as above
```

Replace every "if ctx.Err() != nil → CANCELLED" check written in 0.5.1 that
follows a call with this two-way check (write one helper:
`stopForContext() *stopResult` or similar). Checks *before* a call keep using
the `beforeModelCall`/`beforeToolCall` functions.

## Out of scope

- Budgets across runs, per agent or per project (control plane, M2).
- Warning the model that it is near a limit.
- Provider-side task budgets.

## Pitfalls

- The tool-call limit counts *requested* calls, so the check runs **before** `tool_call_requested` is written.
- `RunState.Usage` is updated when the event is applied, i.e. inside `recorder.add`. Read it after adding `model_call_completed`, not from the response directly, so there is one source of truth.
- `context.WithDeadline` on a parent that is already cancelled returns an already-cancelled ctx: always check the parent ctx first to choose CANCELLED.
- Do not use `time.Sleep` in tests; the wall-clock interrupt test uses a 50 ms deadline and a tool that waits on `ctx.Done()`.
