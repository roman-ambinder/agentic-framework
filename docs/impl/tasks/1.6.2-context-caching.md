# 1.6.2 — Context manager: stable prefix for caching

Size: S · Depends on: 1.6.1, 1.1 · Branch: `task/1.6.2-context-caching` · PR title: `1.6.2: keep request prefixes stable across steps for prompt caching`

## Goal

Prompt caching only helps if each step's request starts with exactly the
same bytes as the previous step's request. After this task:

1. Tools are always sent in the same order (sorted by name).
2. The system prompt never changes during a run.
3. Old tool outputs are elided in batches (with a low-water mark), and an
   output, once elided, stays elided for the rest of the run. Between two
   elision batches, every request's messages start with the previous
   request's messages unchanged.
4. A test proves the prefix property, and a live test shows cache reads.

## Why this matters (read before coding)

A provider caches a request prefix: tools → system → messages, up to a cache
breakpoint (task 1.1 places them). The next request gets a cache hit only if
its bytes up to that point are identical. Three things break that:

- Tool order changes between steps (for example a map iteration or an MCP
  server listing tools in a different order) → the cache misses from the
  very first byte, on every step.
- Changing the system prompt (for example adding the step number) → same.
- Task 1.6.1 rebuilds the elided set from scratch every step. Once the run is
  over budget, every new step pushes the estimate up again, so one more old
  result is elided each step. Each elision changes a message in the middle of
  the conversation, so everything after it misses the cache, on every step.
  Eliding a batch at once (down to a low-water mark) and remembering what was
  elided makes this happen rarely instead of every step.

## Design

### Budget gets a low-water mark

```go
	// LowWaterRatio: when eliding, keep going until the estimate is at or
	// below MaxInputTokens * LowWaterRatio. 0 means 0.7. Must be in (0, 1].
	LowWaterRatio float64
```

In `Build` (1.6.1, step 7), the loop's stop condition changes from
`est <= MaxInputTokens` to `est <= target` where
`target = int64(float64(MaxInputTokens) * ratio)`. Step 5 (the "already
fits" check) still compares with `MaxInputTokens`, so nothing is elided until
the budget is actually exceeded.

### Manager remembers elisions

```go
// Manager builds requests for one run and remembers which tool results it
// has elided, so they stay elided on later steps.
type Manager struct {
	Budget Budget
	elided map[string]bool // tool call IDs whose result is elided
}

func NewManager(b Budget) *Manager

// Prepare is Build plus memory: first it elides every result whose CallID
// is in m.elided (these are not counted as new elisions), then it runs the
// Build algorithm for anything more, and finally records the newly elided
// CallIDs.
func (m *Manager) Prepare(ctx context.Context, req *model.Request) (*model.Request, Stats, error)
```

Implementation: refactor `Build` into an internal
`build(ctx, req, b, elided map[string]bool) (*model.Request, Stats, []string, error)`
that (a) first replaces the content of every tool result whose CallID is in
`elided` with the placeholder, (b) then runs the 1.6.1 algorithm, (c) returns
the CallIDs it newly elided. Public `Build` calls it with a nil map (behaviour
of 1.6.1 unchanged except for the low-water mark). `Prepare` calls it with
`m.elided` and adds the returned IDs to `m.elided`.

The placeholder uses the original byte length, which `Prepare` can always
compute from the full transcript, so step N and step N+1 produce byte-identical
placeholders.

### Harness changes

1. In `Run`, create `mgr := contextmgr.NewManager(effectiveBudget)` once and
   call `mgr.Prepare` in `buildRequest` instead of `contextmgr.Build`.
2. Tools: build the `[]model.ToolSpec` once at the start of `Run` from
   `deps.Tools.Tools()`, sorted with
   `slices.SortFunc(specs, func(a, b model.ToolSpec) int { return strings.Compare(a.Name, b.Name) })`,
   and reuse the same slice for every request.
3. System: set `Request.System = cfg.System` exactly, every step. Never add
   step numbers, times or ids to it. (If 0.5.1 already does this, only add a
   comment saying why.)
4. Resume (task 1.7) starts with a fresh `Manager`: the first request after a
   resume may miss the cache once. That is accepted; write it in the
   `Manager` doc comment.

### Prefix property (what the test checks)

For consecutive requests `r1`, `r2` of one run, where no new elision
happened in between (`Stats.ElidedResults` of `r2`'s `Prepare` call is 0):

- `json.Marshal(r1.Tools) == json.Marshal(r2.Tools)`
- `r1.System == r2.System`
- `len(r2.Messages) > len(r1.Messages)` and for every `i < len(r1.Messages)`:
  `json.Marshal(r1.Messages[i]) == json.Marshal(r2.Messages[i])`

Get the requests from `model.Fake.Requests()`.

## Out of scope

- Persisting the elided set across resume.
- Cache TTL choices, cache pre-warming.
- Per-provider cache breakpoint tuning beyond what 1.1 added.

## Pitfalls

- Map iteration order in Go is random: never build the tool list or any
  request part by ranging over a map without sorting.
- `json.Marshal` of the same Go value is deterministic for structs and
  sorted for map keys, so it is safe to compare in tests; do not compare
  `fmt.Sprintf("%v")` output.
- The placeholder must depend only on the original output (its length), never
  on the step number or the time.
- Keep `Build`'s public behaviour the same as in 1.6.1 apart from the
  low-water mark; other code may call it.
