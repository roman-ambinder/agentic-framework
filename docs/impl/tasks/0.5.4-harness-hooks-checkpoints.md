# 0.5.4 — Harness hooks and checkpoints

Size: S · Depends on: 0.5.1 · Branch: `task/0.5.4-harness-hooks` · PR title: `0.5.4: tool hooks and per-step checkpoints`

## Goal

1. **Hooks:** code (Go, or a plugin from task 0.11) can inspect every tool
   call before it runs and block it with a reason, and observe every result
   after it runs.
2. **Checkpoints:** after every step that ran tool calls, the harness writes
   a `checkpoint` event holding the digest of the run state, so a resumed run
   (task 1.7) can verify its log.

## Design

### Hook (proposed for interfaces.md §6)

```go
// HookDecision is a PreTool hook's answer.
type HookDecision struct {
	Deny   bool
	Reason string // required when Deny is true
}

// Hook observes and may block tool calls. Hooks run in Config.Hooks order.
type Hook interface {
	// Name identifies the hook in events, e.g. "pii-guard". Must match ^[a-z0-9-]{1,40}$.
	Name() string
	// PreTool runs after tool_call_requested and before the policy check.
	PreTool(ctx context.Context, call model.ToolCall, tool toolrouter.Tool) (HookDecision, error)
	// PostTool runs after tool_call_completed. It cannot change the result.
	PostTool(ctx context.Context, call model.ToolCall, res toolrouter.Result) error
}
```

Validate in `Run` (with the other config checks): every hook name matches the
pattern and names are unique; otherwise
`harness: config: invalid hook name "<name>"` / `harness: config: duplicate hook name "<name>"`.

### Where hooks run (in runToolCall)

```
after tool_call_requested (step 3) and the unknown-tool branch (step 4):
  for each hook h in cfg.Hooks:
      d, err := h.PreTool(callCtx, call, tool)
      if err != nil:
          if the context stopped it → stop for context (CANCELLED / WALL_CLOCK)
          add error_occurred{error_class: INTERNAL, message: err.Error(), component: "hook:" + h.Name()}
          → finish(ERROR, "", "hook " + h.Name() + ": " + err.Error())
      if d.Deny:
          add policy_decided{call_id, decision: DENY, rule_id: "hook:" + h.Name(),
                             reason: d.Reason, source: DECISION_SOURCE_HOOK}
          → finish(DENIED, "", fmt.Sprintf("rule hook:%s: %s", h.Name(), d.Reason))
  then the policy check as before (step 5)

after tool_call_completed (step 11):
  for each hook h:
      if err := h.PostTool(callCtx, call, res); err != nil:
          add error_occurred{error_class: INTERNAL, message: err.Error(), component: "hook:" + h.Name()}
          (the run continues: PostTool hooks only observe)
```

Unknown tools skip hooks (nothing runs). A hook that returns `Deny` with an
empty `Reason` gets reason `"denied by hook"`.

### Checkpoints (in the loop)

At the end of each step that ran **all** of its tool calls (i.e. after the
`for` over calls in 0.5.1 step 5k finished without stopping the run):

```
digest, err := r.state.Digest()          // state with every event so far
add checkpoint{step: uint32(step), state_digest: digest, snapshot_ref: ""}
```

No checkpoint after a step that ended the run, and none before the first
model call. `snapshot_ref` stays empty until the sandbox exists (task 1.7).

Checking a checkpoint (used by tests now and by resume later), proposed as an
exported helper in `harness`:

```go
// VerifyCheckpoints folds events and checks that every checkpoint's
// state_digest equals the digest of the state just before it.
// It returns nil if all match.
func VerifyCheckpoints(events []*adlcv1.Event) error
```
Algorithm: `var s eventlog.RunState`; for each event: if it is a checkpoint,
compute `s.Digest()` and compare with its `state_digest` (mismatch →
`fmt.Errorf("harness: checkpoint at seq %d: digest %s, want %s", seq, got, want)`);
then `s.Apply(ev)` (error → return it).

## Out of scope

- Hooks that change a tool call or its result (redaction) — later.
- Hooks around model calls.
- Plugin hooks over gRPC (task 0.11.1 implements `Hook` with a gRPC client).
- Sandbox snapshots in checkpoints (task 1.7).

## Pitfalls

- The digest must be taken **before** the checkpoint event is added (the
  checkpoint describes the state it follows). `VerifyCheckpoints` mirrors this.
- `RunState.Apply` copies the state; take the digest from `r.state` right before calling `r.add(checkpoint)`.
- A hook denial is recorded as `policy_decided` so `eventlog.Fold` removes the call from `PendingToolCalls`; do not invent a new event kind.
- `PostTool` receives the full result (not the capped one).
