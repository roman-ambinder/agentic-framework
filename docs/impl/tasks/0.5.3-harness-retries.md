# 0.5.3 — Harness retries

Size: S · Depends on: 0.5.1 · Branch: `task/0.5.3-harness-retries` · PR title: `0.5.3: retry failed model calls with backoff`

## Goal

A model call that fails with a retryable error (`model.IsRetryable`) is
retried with exponential backoff, up to a limit. Each attempt is recorded:
`model_call_started{attempt: n}` and, on failure,
`model_call_failed{will_retry: …}`. The backoff schedule is deterministic
(no random jitter) so tests can check it exactly. Tool calls are not retried.

## Design

### RetryPolicy (proposed for interfaces.md §6)

```go
// RetryPolicy controls retries of failed model calls.
type RetryPolicy struct {
	// MaxAttempts is the total number of attempts, including the first.
	// 0 means 3. 1 means no retries.
	MaxAttempts int
	// InitialDelay is the wait after the first failed attempt. 0 means 1s.
	InitialDelay time.Duration
	// MaxDelay caps every wait. 0 means 30s.
	MaxDelay time.Duration
}

// withDefaults returns p with zero fields replaced by the defaults.
func (p RetryPolicy) withDefaults() RetryPolicy

// Delay returns how long to wait after failed attempt n (n >= 1):
// min(InitialDelay * 2^(n-1), MaxDelay). Uses the defaults for zero fields.
func (p RetryPolicy) Delay(attempt int) time.Duration
```

Default schedule: attempt 1 fails → wait 1s, attempt 2 fails → wait 2s, then
the third attempt is the last (MaxAttempts 3). With `MaxAttempts: 7`:
1s, 2s, 4s, 8s, 16s, 30s. Guard against overflow: stop doubling once the
value is `>= MaxDelay`.

Negative `MaxAttempts`, `InitialDelay` or `MaxDelay` are treated as zero.

### Retry loop (replaces 0.5.1 steps 5e–5g)

```
p := cfg.Retry.withDefaults()
for attempt := 1; ; attempt++:
    startSeq := add model_call_started{call_id, step, provider, model, attempt}
    t0 := Now(); resp, err := Generate(callCtx, req)
    if err == nil: break → go on to "record model_call_completed" (parent_seq = this attempt's startSeq)
    if the context stopped the call → stop as 0.5.2 says (CANCELLED or WALL_CLOCK);
       still write model_call_failed{will_retry: false} first
    retry := model.IsRetryable(err) && attempt < p.MaxAttempts
    add model_call_failed{call_id, error_class, message, will_retry: retry, http_status}
    if !retry → finish(ERROR, "", err.Error())
    if e := beforeModelCall(...); e != nil → finish budget e        (a budget may have run out)
    if err := deps.Sleep(callCtx, p.Delay(attempt)); err != nil → stop for context (CANCELLED or WALL_CLOCK)
```

The `call_id` stays `m<step>` for every attempt. `step` does not change.
The budget step counter counts only completed calls, so retries do not use up `max_steps`.

## Out of scope

- Random jitter.
- Honouring provider `Retry-After` headers (adapters may add this later inside `model.Error`).
- Retrying tool calls or policy calls.
- Falling back to another provider (task 1.3).

## Pitfalls

- `attempt < p.MaxAttempts` — not `<=` — otherwise you make one attempt too many.
- Each attempt writes its own `model_call_started`; `RunState.ModelCalls` counts attempts, the budget's step counter must not.
- Use `deps.Sleep`, never `time.Sleep`, so tests run instantly.
- `model_call_failed.message` is `err.Error()`; for a `*model.Error` that is the formatted message from task 0.4.
