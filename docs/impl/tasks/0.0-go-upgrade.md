# 0.0 — Upgrade to Go 1.26

Size: S · Depends on: — · Branch: `task/0.0-go-upgrade` · PR title: `0.0: upgrade to Go 1.26 and pin all tools`

## Goal

The repository builds, lints and tests with Go 1.26 (toolchain `go1.26.11`).
Every developer tool, including golangci-lint, is pinned in `tooling/go.mod`
and run with `go tool`, so a fresh machine needs only some Go 1.21+ install.
`modernc.org/sqlite` is at v1.62.0. Nothing else changes behaviour.

Why: the libraries later tasks need (the Anthropic Go SDK v2, the OpenAI Go
SDK v3, the MCP Go SDK v1.8) require Go 1.25 or 1.26. On Go 1.24 they cannot
be used at all.

## Design

**Exact versions (do not substitute others):**

| Tool / module | Version | Note |
|---------------|---------|------|
| Go toolchain | `go1.26.11` | |
| `modernc.org/sqlite` | `v1.62.0` | main module |
| `github.com/bufbuild/buf/cmd/buf` | `v1.74.0` | **not** v1.75.0 — see Pitfalls |
| `google.golang.org/protobuf/cmd/protoc-gen-go` | `v1.36.12` | must equal the protobuf runtime version in `go.mod` |
| `github.com/golangci/golangci-lint/v2/cmd/golangci-lint` | `v2.15.0` | |

**Why `GOTOOLCHAIN := go1.26.11` in the Makefile:** `local` (the old value)
means "use whatever Go is installed, never download". `go1.26.11` means
"use exactly Go 1.26.11; if it is not installed, the go command downloads it
once from the Go module proxy". Every `make` target therefore uses the same
compiler on every machine and in CI.

**Why CI lint uses `make lint`:** the golangci-lint GitHub Action downloads
its own binary, so its version would have to be kept equal to the one in
`tooling/go.mod` by hand. `make lint` uses the pinned version, so there is one
place to change it.

## Steps

1. Create the branch:
   `git fetch --depth=50 origin main && git checkout -b task/0.0-go-upgrade origin/main`
2. In the repo root, run:
   ```bash
   export GOTOOLCHAIN=go1.26.11
   go version
   ```
   Expect `go version go1.26.11 linux/amd64` (or your OS/arch). The first run downloads the toolchain.
3. Set the Go version of the main module:
   `go mod edit -go=1.26 -toolchain=go1.26.11`
4. Upgrade SQLite: `go get modernc.org/sqlite@v1.62.0`, then `go mod tidy`.
   `head -5 go.mod` now shows `go 1.26.0` (or `go 1.26`) and `toolchain go1.26.11`. Either form of the `go` line is fine.
5. Recreate the tooling module. Replace `tooling/go.mod` with exactly:
   ```
   // Pinned developer tools. Run with: go tool -modfile=tooling/go.mod <tool>
   // Kept separate so tool dependencies never enter the main module.
   module github.com/roman-ambinder/agentic-framework/tooling

   go 1.26
   ```
   Delete `tooling/go.sum` (`rm tooling/go.sum`).
6. Add the tools **in this order**, from inside `tooling/`:
   ```bash
   cd tooling
   go get -tool github.com/bufbuild/buf/cmd/buf@v1.74.0
   go get -tool google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12
   go get -tool github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.15.0
   cd ..
   ```
   Then check `grep -A4 '^tool' tooling/go.mod` lists all three, and
   `grep 'bufbuild/buf ' tooling/go.mod` shows `v1.74.0`.
   Do **not** run `go mod tidy` in `tooling/` (AGENTS.md rule 2).
7. Check the tools run:
   ```bash
   go tool -modfile=tooling/go.mod buf --version            # 1.74.0
   go tool -modfile=tooling/go.mod protoc-gen-go --version  # protoc-gen-go v1.36.12
   go tool -modfile=tooling/go.mod golangci-lint version    # ... version 2.15.0 built with go1.26.11 ...
   ```
8. Edit the `Makefile`:
   - Replace `export GOTOOLCHAIN := local` with `export GOTOOLCHAIN := go1.26.11`, and replace its comment with:
     `# Use exactly this Go version; the go command downloads it if missing.`
   - Replace the line `BUF      := go tool -modfile=tooling/go.mod buf` with:
     ```make
     TOOL     := go tool -modfile=tooling/go.mod
     BUF      := $(TOOL) buf
     LINT     := $(TOOL) golangci-lint
     ```
   - In the `lint` target replace `golangci-lint run ./...` with `$(LINT) run ./...`.
   - In the `fmt` target replace `golangci-lint fmt ./...` with `$(LINT) fmt ./...`.
   - Update the comment above `tidy` if it mentions Go 1.24 (keep the rule; drop the version number).
9. Edit `.github/workflows/ci.yml`, job `lint`: replace the step that uses
   `golangci/golangci-lint-action@v8` (and its `with:` block) with:
   ```yaml
      - name: lint
        run: make lint
   ```
   Keep the `actions/checkout` and `actions/setup-go` steps. Leave the other jobs unchanged.
10. `README.md`: change "Requires Go 1.24+ and golangci-lint v2." to
    "Requires Go 1.21 or newer; `make` downloads Go 1.26.11 and all tools on first use."
11. Work plan `docs/plans/2026-11-13-adlc-work-plan.md` §7: replace the
    "**Go version:**" bullet with
    "**Go version:** the repo targets Go 1.26 (toolchain go1.26.11, task 0.0). Tools are pinned in `tooling/go.mod`."
12. Regenerate protobuf code and confirm nothing changed: `make proto && git status --short gen/`
    → no output. If `gen/` changed, the protoc-gen-go version is wrong; go back to step 6.
13. Run `make ci` (see Verify). Fix only formatting issues it reports (`make fmt`); if it reports anything else, stop and report.
14. Commit (message below), push, open the PR.

## Pitfalls

- **buf v1.75.0 does not work with protoc-gen-go v1.36.12 in one module.**
  buf v1.75.0 needs a newer pre-release of `google.golang.org/protobuf`; adding
  protoc-gen-go v1.36.12 afterwards silently downgrades buf to v1.74.0. That
  is why this brief pins v1.74.0 directly. protoc-gen-go must match the
  protobuf runtime in the main `go.mod` (v1.36.12), otherwise `gen/` changes.
- `go get -tool` prints "downgraded …" lines for buf's dependencies. That is expected.
- `tooling/go.mod`'s `go` line may become `go 1.26.7` (buf's minimum). That is fine.
- Do not run `go mod tidy` in `tooling/` — it pulls test-only dependencies at their newest versions.
- The first `make` run downloads Go 1.26.11 and all tools; it can take several minutes. Do not interrupt it.
- The system-wide `golangci-lint` (if one is installed) is no longer used. Do not call it directly.
