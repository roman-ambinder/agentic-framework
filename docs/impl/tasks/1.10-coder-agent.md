## Design

### Agent files

Use the field names defined by brief 0.9.1. The **values** below are fixed.
If 0.9.1 has no way to load the system prompt from a file (`system_file`) or
to read the model name from an environment variable (`${ADLC_ANTHROPIC_MODEL}`),
stop and report: both are needed (the prompt must not be copied into two
files, and model ids are kept out of the repository).

`agents/sdlc/coder.anthropic.yaml` (field names as in 0.9.1; shown here with the names 0.9.1 is expected to use):

```yaml
id: coder-anthropic
version: 1
system_file: coder.prompt.md          # relative to this file
model:
  provider: anthropic
  name: ${ADLC_ANTHROPIC_MODEL}       # set in your shell; not committed
  max_tokens: 16000
  effort: high
  price:                              # micro-USD per million tokens; fill from the provider's price page
    input_per_mtok: 0                 # see Step 4
    output_per_mtok: 0
    cache_read_per_mtok: 0
    cache_write_per_mtok: 0
budget:
  max_steps: 60
  max_tokens: 3000000
  max_wall_clock: 20m
  max_usd: 2.00
  max_tool_calls: 150
policy:
  default: deny
  rules:
    - {id: read,  risk: read,        decision: allow}
    - {id: write, risk: write_local, decision: allow}
    - {id: exec,  risk: exec,        decision: allow}
```

`coder.openai.yaml` is identical except `id: coder-openai`,
`provider: openai`, `name: ${ADLC_OPENAI_MODEL}`, and its own prices.

The tools are not listed in the agent file: `adlc eval` (task 1.8) gives the
agent the sandbox tool router from task 1.5. All of those tools run inside the
sandbox, which is why `exec` and `write_local` are allowed. Nothing with risk
`write_external` or `irreversible` is allowed.

### System prompt (`agents/sdlc/coder.prompt.md`, exact text for iteration 0)

Replace `<TOOLS>` with one line per tool from brief 1.5: `- <name>: <one-line description>`.

```markdown
You are a software engineer fixing a reported bug in a Go repository.
The repository is in /workspace. You can only act through the tools below.

Tools:
<TOOLS>

Work in this order:
1. Read the issue carefully. Write down, in one or two sentences, what behaviour is wrong and what the correct behaviour is.
2. Explore: list the files, find the code involved, read it. Do not change anything yet.
3. Reproduce: add a small test that fails because of the bug, in the package that contains the bug, in a new file named <package>_issue_test.go. Run it and confirm it fails for the reason described in the issue.
4. Fix: make the smallest change to non-test code that makes your test pass. Do not rewrite unrelated code, rename things, or reformat files.
5. Check: run `go build ./...` and `go test ./...`. Everything must pass, including tests that existed before.
6. Finish: reply with a short summary: the cause of the bug, the files you changed, and the test you added. Do not call any tool in that final reply.

Rules:
- Keep the diff minimal. Do not modify existing tests unless the issue says they are wrong.
- There may be tests you cannot see that check the fix; fix the behaviour described in the issue, not just your own test.
- Do not download dependencies; there is no network.
- If a command fails, read the error before trying again. Do not repeat the same failing command unchanged.
- Stop as soon as the checks in step 5 pass.
```

### Iteration log (`docs/experiments/coder-agent.md`)

Starts with:

```markdown
# Coder agent experiments

Suite: evals/suites/go-bugs · G1 thresholds (work plan §5): pass@1 ≥ <x>, median cost ≤ $<y>, median steps ≤ 40

| It. | Date | Change (one) | Hypothesis | Provider | Solved | pass@1 | Median $ | Median steps | Total $ | Top failure cause | Decision |
|-----|------|--------------|------------|----------|--------|--------|----------|--------------|---------|-------------------|----------|
```

One row per provider per iteration. **Decision** is `baseline`, `keep` or `revert`.
Below the table, one section per iteration: `## Iteration N` with the report
path, the failure causes per failed bug (table: bug, provider, cause, one-line
evidence from the trace), and what you will change next and why.

### Failure causes (use exactly these labels)

| Label | Meaning |
|-------|---------|
| `wrong-diagnosis` | changed the wrong code or misunderstood the issue |
| `no-repro` | never ran a test that showed the bug |
| `broke-build` | left code that does not compile |
| `broke-other-tests` | hidden test passes but other tests fail |
| `partial-fix` | fixed the case in its own test but not the general behaviour |
| `budget` | stopped with `BUDGET_EXHAUSTED` |
| `tool-misuse` | most steps wasted on failing tool calls |
| `gave-up` | ended with `COMPLETED` without a working fix |
| `refused-or-error` | stopped with `ERROR` |
| `infra` | result has `error` (sandbox, Docker) — not the agent's fault |

### Decision rules

- **keep** a change if, summed over both providers, solved increases by ≥ 1 and median cost does not rise by more than 25 %, **or** solved stays equal and median cost or median steps fall by ≥ 15 %.
- Otherwise **revert** it (restore the previous prompt or file exactly).
- If solved changes by exactly 1 bug in either direction, run the iteration a second time before deciding, and decide on the sum of both runs (results vary from run to run).
- **Stop iterating** when either: both of the G1 thresholds pass@1 and median cost are met by at least one provider; or 5 iterations in a row are reverted; or total spend in this task reaches $60 (sum the `Total $` column).

### One change per iteration

Candidate changes, in the suggested order (pick by what the top failure cause says):
1. Prompt wording for the step the failures point at.
2. `effort` (`medium` vs `high`).
3. `max_tokens` per call.
4. Budget (`max_steps`, `max_usd`) — only if `budget` is the top cause.
5. Tool descriptions (they live in task 1.5's code: open a separate PR for that change, then re-run).

Never change two things at once. Never change the suite, the graders or the hidden tests to improve the score.

## Steps

1. Branch from the latest `main`.
2. Read brief 0.9.1 and check that `system_file` and `${ENV}` in `model.name` exist. If not, stop and report.
3. Read brief 1.5 and copy the exact tool names and descriptions into the `<TOOLS>` list of the prompt.
4. Fill in prices: open the provider's official pricing page for the model you will set in `ADLC_ANTHROPIC_MODEL` / `ADLC_OPENAI_MODEL`, convert $/million tokens to micro-USD per million tokens (multiply by 1,000,000; e.g. $3.00 → `3000000`), and add a YAML comment above `price:` with the page's URL and the date you read it.
5. Add the test `TestLoadRepoAgents` to `internal/agentconfig` (in a new file `repo_agents_test.go`): it sets
   `ADLC_ANTHROPIC_MODEL` and `ADLC_OPENAI_MODEL` to `test-model` with `t.Setenv`, finds every `*.yaml` under
   `../../agents` with `filepath.WalkDir`, calls `agentconfig.Load` on each, and fails with the file name on any error.
   Run `go test ./internal/agentconfig/ -run TestLoadRepoAgents -v`; both coder files must load.
6. Set the environment: `ADLC_ANTHROPIC_MODEL`, `ADLC_OPENAI_MODEL`, and the two providers' API key variables (names as in tasks 1.1 and 1.2). Never commit them.
7. Before each eval run, estimate the worst-case spend: `bugs × providers × max_usd` (10 × 2 × $2 = $40). If that plus the spend so far would exceed $60, run fewer bugs (`--bugs`) or stop.
8. **Iteration 0 (baseline):**
   ```bash
   make build
   ./bin/adlc eval evals/suites/go-bugs \
     --agents agents/sdlc/coder.anthropic.yaml,agents/sdlc/coder.openai.yaml \
     --out evals/results/coder-it0.json
   ```
   Fill the log rows from the summary lines (`./bin/adlc eval-report evals/results/coder-it0.json`).
9. For every failed (not solved) result: `./bin/adlc trace <run_id>`, read it, assign one failure cause label with one line of evidence. Fill the iteration section.
10. Choose **one** change (rules above), make it, write the hypothesis in the log, re-run with `--out evals/results/coder-it<N>.json`, fill rows, decide keep/revert, and apply the decision to the files.
11. Repeat 9–10 until a stop condition is met.
12. Write a final section `## Result for gate G1` in the log: the best iteration per provider, its pass@1 per difficulty, median cost, median steps, the top 3 failure causes overall, and which row of the G1 table in the work plan §5 applies.
13. Add a row to the work plan §8: `| <date> | Gate G1 | <provider>: pass@1 <x>, median $<y>, median steps <z>; G1 row: "<row text>" → M2 is <M2-Q or M2-C> |`.
14. Commit the prompt, agent files, the agentconfig test and the experiment log (not `evals/results/`, which is git-ignored). Open the PR; paste the final section into its description.

## Out of scope

- Changing the harness, context manager, tools or graders (except tool descriptions via a separate PR, see "One change per iteration").
- Adding bugs to the suite.
- Multi-agent setups, planning steps or memory (those are M2-Q/M3 ideas; note them in the log as ideas if the traces suggest them).

## Pitfalls

- Model ids and API keys go in environment variables only; nothing provider-account-specific is committed.
- Results vary between runs; one bug up or down is noise until repeated (decision rules).
- Watch spend: a 10 × 2 run can cost up to `20 × max_usd`. Check `Total $` after every run.
- A `infra` failure is not an agent failure: fix the environment and re-run that bug instead of changing the prompt.
- Do not tune the prompt to a single bug's details (for example naming a function from one issue). Changes must make sense for any Go bug.
- Reverting means restoring the previous text exactly (`git checkout -- agents/sdlc/coder.prompt.md` before committing, or keep a copy).
