# M3 — task list and shared decisions

M3 is the orchestrator and the SDLC pipeline (work plan §6, design §3.5 and
§4): a **workflow** of tasks, each run by an agent, coordinated as a graph,
with a review loop and a human gate before release.

**Build gate.** The work plan says M3 needs evidence that a single agent is
reliable enough to chain (gate G1, plan §9). These briefs are written before
G1 so building can start as soon as G1 is recorded; if G1 says the single
agent is not good enough, fix that first (M2-Q) and keep these briefs.

Each task has a brief in `tasks/`; this file holds the decisions the briefs
share and the exact API they build. If a brief disagrees with this file, this
file wins and the brief is fixed.

## Shared decisions

1. **A workflow is a file, the engine is a library, the CLI is thin.**
   Workflows are YAML (`workflows/*.yaml`, language-neutral, design §3.5).
   Package `internal/workflow` loads them, runs them and folds their history.
   `internal/cli` wires dependencies (like `adlc eval` does for
   `internal/evals`). Import rule: `internal/workflow` may import
   `internal/evals`, `internal/eventlog`, `internal/sandbox`; **`internal/evals`
   and `internal/controlplane` never import `internal/workflow`** (cycle).
2. **Workflow history is an event log, but not in the run database.** The
   run store (`.adlc/events.db`) requires every log to start with
   `run_started`, and commands such as `adlc cost` and `adlc approvals` fold
   every log in it. Workflow events therefore go to their own file,
   `.adlc/workflows.db` (flag `--workflow-db`, constant
   `defaultWorkflowDBPath` in `internal/cli`), opened with the same
   `eventlog.Store` and the option `eventlog.WithFirstKind("workflow_started")`
   (task W.2). Each workflow is one log whose `run_id` is the workflow id.
   Child runs are ordinary runs in `.adlc/events.db`. The proto already has
   `RunStarted.workflow_id` and `RunStarted.task_id`; **W.5 adds
   `harness.Config.WorkflowID` and `Config.TaskID`** so child runs set them.
3. **State is a fold.** `workflow.Fold(events)` gives `workflow.State`; the
   engine never keeps state anywhere else. `adlc workflow resume` folds the
   log, reads the child runs' states and continues. At most one
   `task_started` is open at a time. **Crash recovery:** on resume, an open
   `task_started` is closed with `task_finished{ERROR, "interrupted"}` and the
   same attempt is started again (decision 8); the sandbox named in its
   `task_started.sandbox_id` is destroyed; the workspace is always rebuilt
   from the last commit recorded in the log. The engine creates a run's
   sandbox before writing `task_started`; if that fails, nothing is written
   and the workflow stays running (resume tries again).
4. **One workspace per workflow, advanced by commits on the host.** The
   workspace is `<base>/<workflow-id>/workspace/` (a plain directory, never
   containing `.git`) plus a separate git directory `<base>/<workflow-id>/git/`
   (`<base>` = `<dir of --workflow-db>/workflows`, default `.adlc/workflows`).
   Every git command the engine runs passes `--git-dir` explicitly, passes
   `--work-tree` where the command uses one, sets `-c core.hooksPath=/dev/null`
   and `-c core.fsmonitor=false`, drops inherited `GIT_*` variables and uses
   the identity `adlc <adlc@localhost>` (the same as the eval base commits).
   The base commit is `git archive` of the `repo` input's HEAD tree (committed
   files only); the HEAD hash is recorded as `WorkflowStarted.source_commit`.
   A task copies the workspace into a fresh sandbox, runs its agent, copies
   `/workspace` out, **removes every `.git` at any depth** (an agent must not
   be able to plant git config that runs on the host — the lesson of task
   1.8), replaces the workspace and commits it as
   `task <task-id> attempt <a>[ round <r>]` (`--allow-empty`).
5. **Tasks run one at a time**, in a fixed topological order (ties broken by
   the order in the file). Parallel tasks need separate workspaces and a merge
   step; that is later work.
6. **Agents talk through artifacts, not chat history** (design §3.5). A task's
   prompt is a Go `text/template` with four functions: `input "name"` (a
   `text` input's value, or a `file` input's content from the snapshot taken
   at Start; a `dir` input is an error), `file "path"` (a file in the
   workspace), `result "task"` (the final message of an earlier task's last
   producer run), `diff "task"` (the change that task committed). Every value
   is capped at 64 KiB with a marker. The CLI makes `dir` and `file` input
   values absolute before Start; `file` inputs are copied to
   `<base>/<id>/inputs/<name>` so a resumed workflow renders the same prompts.
7. **Budgets nest.** A workflow has a total budget (USD, tokens, wall clock).
   A run's budget is the field-wise minimum of the positive values of the
   agent's own budget, the task's `budget:` and what is left of the
   workflow's (spend = the sum of all child runs' usage; wall clock = time
   spent inside task runs, so parked time does not count). A task never
   starts when the workflow budget is spent; the workflow then stops with
   outcome `budget_exhausted`.
8. **Checks and attempts.** A task may list `checks:` (shell commands run with
   `sh -c` in a fresh sandbox on the committed workspace, first failure stops,
   10 minutes each). A producer run passes only if it completed and every
   check exited 0. A failed attempt is retried, up to `attempts` per round,
   from the failed attempt's commit, with the check output added to the
   prompt. Attempt numbers count up across the whole task. An `ERROR`
   (infrastructure failure or interruption) does **not** use up an attempt:
   the same attempt number starts again with a new run.
9. **The review loop is a task property.** `review:` on a producer task names
   a critic agent and `max_rounds`. After the producer passes its checks, the
   critic runs on the diff since the task's base commit; its final message
   ends with `VERDICT: APPROVE` or `VERDICT: CHANGES` (a missing verdict
   counts as CHANGES). The critic never commits. On CHANGES the producer runs
   again with the critic's message. After `max_rounds` without approval the
   task's last `task_finished` is the critic's `CHANGES_REQUESTED` and the
   workflow ends with outcome `REVIEW_EXHAUSTED`. With review, rounds are
   numbered from 1; without review the round is 0.
10. **Human gates park the workflow.** `gate: approval` on a task parks the
    workflow before that task's first start (event `gate_requested`, status
    `awaiting_approval`, process exits 0). `adlc workflow approve WORKFLOW_ID
    TASK_ID FILE [--reject]` records `gate_resolved` and continues. A child
    run that parks for a tool approval (task C.1) ends its task run with
    `task_finished{AWAITING_APPROVAL}` and keeps its sandbox (its id is in the
    event). **W.5 extends `adlc approve`** for runs with a `workflow_id`: it
    finds the kept sandbox, attaches the sandbox tools and uses the run's
    recorded budget. `adlc workflow resume` then writes a new `task_started`
    with the **same run id** (a continuation), copies that sandbox out and
    goes on.
11. **Release leaves the sandbox as a local branch, never a push.** A task of
    `kind: export` has no agent. The engine creates branch
    `adlc/<workflow-id>` in the `repo` input's repository: parent =
    `source_commit`, tree = the source tree plus the workflow's diff from base
    to its last commit, built in a private index (`read-tree`, `apply
    --cached`, `write-tree`, `commit-tree`, `update-ref` refusing an existing
    branch). The person's index, working tree, HEAD and current branch are
    untouched; hooks are off; nothing is pushed. If the repo's HEAD moved
    since Start, the branch is still based on `source_commit` (what checks
    and review saw) and the detail says so.
12. **Schema changes are additive** (AGENTS.md rules 4–5): six new event
    payloads, numbers 23–28, recorded in `interfaces.md` §10 by task W.2.
    W.2 also updates `contracts/contracts_test.go` (a sample per new kind) and
    `internal/eventlog/fold_test.go` (`TestEveryKindIsHandled` skips the six
    workflow kinds; `eventlog.Fold` counts them as unknown, unchanged).
13. **Pipeline evals reuse the eval runner and graders.** `adlc eval
    SUITE_DIR --workflow FILE` runs the workflow once per bug, then grades the
    final workspace exactly like a single-agent run, so `adlc eval-compare`
    can compare the pipeline with the single coder agent on the same suite.
    The loop lives in `internal/evals` behind a callback; the CLI wires the
    engine (decision 1's import rule).
14. **Ids.** Workflow id = `<name>-v<version>-<UTC yyyymmddThhmmssZ>-<6 hex>`
    (no `@`; name at most 20 characters, version at most 999999999), or
    `--id` matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,57}$` (no dots, so every id
    is also a valid git branch component for export). Child run id =
    `<workflow-id>-<n>`, where n counts the child runs started in the workflow
    (1, 2, …; a continuation keeps its id). Both fit the repository's run-id
    rule `^[A-Za-z0-9._-]{1,64}$`, so `adlc kill run`, `trace` and `cost`
    work on them unchanged.

### Workflow file (task W.1)

Illustrative; W.6 writes the real `workflows/sdlc.yaml`.

```yaml
name: sdlc                     # ^[a-z0-9][a-z0-9-]*$, at most 20 characters
version: 1                     # 1..999999999
inputs:                        # names the CLI must supply with --input name=value
  - name: repo
    kind: dir                  # dir | file | text
  - name: issue
    kind: file
budget:                        # the whole workflow; every field optional
  max_usd: 3.00
  max_tokens: 6000000          # keep above every agent's own max_tokens
  max_wall_clock: 1h
tasks:
  - id: spec                   # ^[a-z0-9][a-z0-9-]*$, at most 64 characters, unique
    agent: ../agents/sdlc/spec.anthropic.yaml   # path relative to this file, or NAME@N / NAME@ENV (task C.4)
    prompt: |
      Write a specification for this issue:
      {{ input "issue" }}
  - id: implement
    agent: ../agents/sdlc/coder.anthropic.yaml
    depends_on: [spec]
    prompt: |
      Implement this specification:
      {{ result "spec" }}
    checks:
      - go build ./...
      - go test ./...
    attempts: 2                # 1..5 per round, default 1
    budget: { max_usd: 1.50 }  # narrows the agent's budget for this task's runs
    review:
      critic: ../agents/sdlc/reviewer.anthropic.yaml
      max_rounds: 2            # 1..5
  - id: release
    kind: export               # agent (default) | export
    depends_on: [implement]
    gate: approval             # none (default) | approval
```

`eventlog` (task W.2): `func WithFirstKind(kind string) Option` — the kind
the first event of every log must have (default `"run_started"`), and
`Kind` returns `"workflow_started"`, `"task_started"`, `"task_finished"`,
`"gate_requested"`, `"gate_resolved"`, `"workflow_completed"` for the new
payloads. `eventlog.Fold` is unchanged.

**Sequencing rules the fold enforces** (W.2), relied on by W.3–W.5:
- one `task_started` open at a time; `task_finished` matches its task, role,
  attempt, round and run id;
- a producer start has attempt = previous producer attempt + 1, except after
  a `task_finished{ERROR}` (same attempt again, new run id) and after
  `task_finished{AWAITING_APPROVAL}` (same attempt, round and **run id**: a
  continuation);
- a critic start follows a producer `PASSED` in the same round (or a critic
  `ERROR`/`AWAITING_APPROVAL` as above), with that producer's attempt;
- a producer start in round r+1 follows a critic `CHANGES_REQUESTED` in round r;
- a gate is requested before the task's first start, at most once, and must be
  resolved (approved) before the task starts;
- nothing follows `workflow_completed`.

### Pipeline evals (task W.6)

`adlc eval SUITE_DIR --workflow FILE [--bugs ...] [--repeat N]`: per bug,
inputs are `repo` = the prepared buggy workspace and `issue` = the bug's
`issue.md` (an eval workflow must declare exactly these two inputs); gates
auto-approve; export tasks are skipped; the final workspace is graded by the
existing graders. Eval workflows use the eval work directory as
`Options.BaseDir` (not `.adlc/workflows`), so `--keep-workspaces` and the
temporary work directory apply to them as to single-agent runs.
`Result.Agent` = `<name>@<version>`, `Result.Provider` =
`"workflow"`, `Result.RunID` = the workflow id, `Result.AgentDigest` =
`Workflow.Digest`. Because `Result.RunID` is not a run in the run log,
`adlc eval-report --failures` classifies workflow results from their outcome
and grade without reading events. `--dry-run` worst case = the workflow's
`budget.max_usd` × bugs × repeat; a workflow without `max_usd` is refused.
