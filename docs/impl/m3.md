# M3 — task list and shared decisions

M3 is the orchestrator and the SDLC pipeline (work plan §6, design §3.5 and
§4): a **workflow** of tasks, each run by an agent, coordinated as a graph,
with a review loop and a human gate before release.

**Build gate.** The work plan says M3 needs evidence that a single agent is
reliable enough to chain (gate G1, plan §9). These briefs are written before
G1 so building can start as soon as G1 is recorded; if G1 says the single
agent is not good enough, fix that first (M2-Q) and keep these briefs.

Each task has a brief in `tasks/`; this file holds the decisions the briefs
share and the exact API they build. If a brief disagrees with this file, this
file wins and the brief is fixed.

## Shared decisions

1. **A workflow is a file, the engine is a library, the CLI is thin.**
   Workflows are YAML (`workflows/*.yaml`, language-neutral, design §3.5).
   Package `internal/workflow` loads them, runs them and folds their history.
   `internal/cli` only wires dependencies (like `adlc eval` does for
   `internal/evals`).
2. **Workflow history is an event log, but not in the run database.** The
   run store (`.adlc/events.db`) requires every log to start with
   `run_started`, and commands such as `adlc cost` and `adlc approvals` fold
   every log in it. Workflow events therefore go to their own file,
   `.adlc/workflows.db` (flag `--workflow-db`, constant
   `defaultWorkflowDBPath` in `internal/cli`), opened with the same
   `eventlog.Store` and the option `eventlog.WithFirstKind("workflow_started")`
   (task W.2). Each workflow is one log whose `run_id` is the workflow id.
   Child runs are ordinary runs in `.adlc/events.db`, with
   `RunStarted.workflow_id` and `RunStarted.task_id` set (these fields exist).
3. **State is a fold.** `workflow.Fold(events)` gives `workflow.State`; the
   engine never keeps state anywhere else. `adlc workflow resume` folds the
   log, reads the child runs' states and continues from there, so a crash at
   any point loses at most the task that was running.
4. **One workspace per workflow, advanced by commits on the host.** The
   workspace is `.adlc/workflows/<workflow-id>/workspace/` (a plain
   directory, never containing `.git`) plus a separate git directory
   `.adlc/workflows/<workflow-id>/git/`. Every git command the engine runs
   uses `--git-dir` and `--work-tree` explicitly and `-c core.hooksPath=/dev/null`.
   A task copies the workspace into a fresh sandbox, runs its agent, copies
   `/workspace` out, **drops any `.git` the agent created** (an agent must
   not be able to plant git config that runs on the host — the lesson of
   task 1.8), replaces the workspace with the result and commits it as
   `task <task-id> attempt <n>`. The commit hash is recorded in the event.
5. **Tasks run one at a time**, in a fixed topological order (ties broken by
   the order in the file). Parallel tasks need separate workspaces and a
   merge step; that is later work (out of scope for M3).
6. **Agents talk through artifacts, not chat history** (design §3.5). A task's
   prompt is a Go `text/template` with four functions: `input "name"` (a
   workflow input), `file "path"` (a file in the workspace), `result "task"`
   (the final message of an earlier task), `diff "task"` (the change an
   earlier task committed). Every value is capped at 64 KiB with a marker.
7. **Budgets nest.** A workflow has a total budget (USD, tokens, wall clock).
   Before a task starts, its run budget is the agent's own budget, narrowed
   by the task's `budget:` and by what is left of the workflow's. A task never
   starts when the workflow budget is spent; the workflow then stops with
   outcome `budget_exhausted`.
8. **Acceptance checks are commands, not opinions.** A task may list
   `checks:` (shell commands run in a fresh sandbox on the committed
   workspace, e.g. `go test ./...`). A task passes only if its run completed
   and every check exited 0. A failed task is retried up to `attempts` times
   with the check output added to the prompt.
9. **The review loop is a task property.** `review:` on a producer task names
   a critic agent and `max_rounds`. After the producer passes its checks, the
   critic runs on the diff; its final message ends with a line
   `VERDICT: APPROVE` or `VERDICT: CHANGES`. On `CHANGES` the producer runs
   again with the critic's message; after `max_rounds` without approval the
   task fails with outcome `review_exhausted`.
10. **Human gates park the workflow.** `gate: approval` on a task parks the
    workflow before that task (event `gate_requested`, workflow status
    `awaiting_approval`, process exits 0). `adlc workflow approve
    WORKFLOW_ID TASK_ID [--reject]` records `gate_resolved` and continues.
    A child run that parks for a tool approval (task C.1) parks the workflow
    the same way; after `adlc approve` finishes that run, `adlc workflow
    resume` picks it up.
11. **Release leaves the sandbox as a local branch, never a push.** A task of
    `kind: export` has no agent: the engine creates branch
    `adlc/<workflow-id>` in the target repository from the workspace's final
    tree, using host-side git with hooks disabled. Pushing and opening a pull
    request stay with the person (design §3.6: changes leave only as a diff
    or PR, never by pushing from the sandbox).
12. **Schema changes are additive** (AGENTS.md rules 4–5): six new event
    payloads, numbers 23–28, recorded in `interfaces.md` §10 by task W.2.
13. **Pipeline evals reuse the eval runner and graders.** `adlc eval
    --workflow FILE` runs the workflow once per bug, then grades the final
    workspace exactly like a single-agent run, so `adlc eval-compare` can
    compare the pipeline with the single coder agent on the same suite.

## The API (package `internal/workflow`)

Briefs use exactly these names. A brief may add unexported helpers, never
different exported names.

### Workflow file (task W.1)

```yaml
name: sdlc                     # ^[a-z0-9][a-z0-9-]*$
version: 1                     # >= 1; workflow id prefix is name@version
inputs:                        # names the CLI must supply with --input name=value
  - name: repo
    kind: dir                  # dir | file | text
  - name: issue
    kind: file
budget:                        # the whole workflow; every field optional
  max_usd: 2.00
  max_tokens: 2000000
  max_wall_clock: 1h
tasks:
  - id: spec                   # ^[a-z0-9][a-z0-9-]*$, unique
    agent: ../agents/sdlc/spec.yaml    # path relative to this file, or NAME@N / NAME@ENV (task C.4)
    prompt: |
      Write spec.md for this issue:
      {{ input "issue" }}
  - id: implement
    agent: ../agents/sdlc/coder.anthropic.yaml
    depends_on: [spec]
    prompt: |
      Implement the change described in spec.md:
      {{ file "spec.md" }}
    checks:
      - go build ./...
      - go test ./...
    attempts: 2                # 1..5, default 1
    budget: { max_usd: 0.80 }  # narrows the agent's budget for this task
    review:
      critic: ../agents/sdlc/reviewer.yaml
      max_rounds: 2            # 1..5
  - id: release
    kind: export               # agent (default) | export
    depends_on: [implement]
    gate: approval             # none (default) | approval
```

### Events (task W.2; `contracts/proto/adlc/v1/events.proto`, additive)

```proto
// in Event.payload:
WorkflowStarted   workflow_started   = 23;
TaskStarted       task_started       = 24;
TaskFinished      task_finished      = 25;
GateRequested     gate_requested     = 26;
GateResolved      gate_resolved      = 27;
WorkflowCompleted workflow_completed = 28;

message WorkflowStarted {
  string workflow_name = 1;
  uint32 workflow_version = 2;
  string workflow_digest = 3;      // Workflow.Digest
  map<string, string> inputs = 4;  // as given on the command line
  Budget budget = 5;               // max_usd_micros, max_tokens, max_wall_clock only
  string base_commit = 6;          // workspace commit before the first task
}

enum TaskRole {
  TASK_ROLE_UNSPECIFIED = 0;
  TASK_ROLE_PRODUCER = 1;   // the task's own agent
  TASK_ROLE_CRITIC = 2;     // the review agent (task W.4)
  TASK_ROLE_EXPORT = 3;     // kind: export (task W.5)
}

message TaskStarted {
  string task_id = 1;
  TaskRole role = 2;
  uint32 attempt = 3;       // 1-based, per task
  uint32 round = 4;         // review round, 1-based; 0 without review
  string run_id = 5;        // child run id; "" for export
  Budget budget = 6;        // the run budget after nesting
}

enum TaskOutcome {
  TASK_OUTCOME_UNSPECIFIED = 0;
  TASK_OUTCOME_PASSED = 1;
  TASK_OUTCOME_CHECKS_FAILED = 2;
  TASK_OUTCOME_RUN_FAILED = 3;      // child run stopped other than completed
  TASK_OUTCOME_AWAITING_APPROVAL = 4; // child run parked (task C.1)
  TASK_OUTCOME_CHANGES_REQUESTED = 5; // critic said CHANGES (task W.4)
  TASK_OUTCOME_ERROR = 6;           // engine or infrastructure failure
}

message TaskFinished {
  string task_id = 1;
  TaskRole role = 2;
  uint32 attempt = 3;
  uint32 round = 4;
  string run_id = 5;
  TaskOutcome outcome = 6;
  string detail = 7;        // check output tail, critic verdict line, or error
  string commit = 8;        // workspace commit after this run; "" if none
}

message GateRequested {
  string task_id = 1;
  string summary = 2;       // what the approver is shown
}

message GateResolved {
  string task_id = 1;
  bool approved = 2;
  string resolved_by = 3;
  string comment = 4;
}

enum WorkflowOutcome {
  WORKFLOW_OUTCOME_UNSPECIFIED = 0;
  WORKFLOW_OUTCOME_COMPLETED = 1;
  WORKFLOW_OUTCOME_FAILED = 2;            // a task failed after its attempts
  WORKFLOW_OUTCOME_BUDGET_EXHAUSTED = 3;
  WORKFLOW_OUTCOME_REJECTED = 4;          // a gate was rejected
  WORKFLOW_OUTCOME_REVIEW_EXHAUSTED = 5;  // task W.4
  WORKFLOW_OUTCOME_CANCELLED = 6;
}

message WorkflowCompleted {
  WorkflowOutcome outcome = 1;
  string detail = 2;
}
```

`eventlog` (task W.2): `func WithFirstKind(kind string) Option` — the kind
the first event of every log must have (default `"run_started"`), and
`Kind` returns `"workflow_started"`, `"task_started"`, `"task_finished"`,
`"gate_requested"`, `"gate_resolved"`, `"workflow_completed"` for the new
payloads. `eventlog.Fold` is unchanged: workflow events never reach it.

### Engine (task W.3; W.4 and W.5 extend it)

// final state. The CLI wires the harness, model, tools and kill switch, the

type TaskRun struct {
	RunID      string
	WorkflowID string
	Task       Task
	Role       adlcv1.TaskRole
	AgentRef   string        // Task.Agent, or Review.Critic for critics

Exit codes like `adlc run`: 0 completed or parked (status line says which),
2 finished other than completed, 1 usage or infrastructure error.

### Pipeline evals (task W.6)

`adlc eval --workflow FILE [--bugs ...] [--repeat N]`: per bug, inputs are
`repo` = the prepared buggy workspace and `issue` = the bug's `issue.md`;
gates auto-approve; export tasks are skipped; the final workspace is graded
by the existing graders. `Result.Agent` is the workflow id prefix
`<name>@<version>`, `Result.Provider` is `"workflow"`, and `Result.RunID` is
the workflow id.
